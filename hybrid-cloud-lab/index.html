Section 01

Why I built it

Most hybrid cloud write-ups stop at "the tunnel is up". The real work starts after that: routes that quietly fail to arrive, packets that ping fine but hang on transfer, and a cloud side that nobody can rebuild because it was clicked together by hand.

I wanted to do it properly, end to end. A route-based IPsec tunnel from my lab to Google Cloud, eBGP carrying the routes instead of static entries, filters on both sides, alerts when something drops, and the cloud side described as code.

I built it on OPNsense first, to learn it. Then, instead of switching over, I built the same thing again on VyOS, on a second public address, running side by side. Two platforms doing the same job is the fastest way I know to understand what each one is really doing.

Section 02

The design

Each router holds one IKEv2 tunnel to a single Google Cloud HA VPN gateway, one per gateway interface. The tunnel is bound to a virtual tunnel interface, so the routing table decides what goes in, not a fixed list of networks. eBGP runs over the tunnel on a link-local /30 and talks to Cloud Router, which writes the learned routes into the VPC.

Three private AS numbers, one each for Google, OPNsense, and VyOS, make every session external BGP, which brings loop protection for free. Phase 1 and phase 2 use AES-256, SHA-256, and DH group 14. The tunnel interfaces run at MTU 1400 with MSS clamped to 1360, because a ping that works while file transfers hang is the classic hybrid fault.

Overlap is silent. Google stops you creating overlapping subnets inside one VPC, but nothing stops overlap between the lab and the cloud. Pick the ranges once and write them down.

Section 03

Built in gates

Every phase ends with a gate: a short test that must pass before the next phase starts. Almost every painful moment came from a problem in one layer showing up as a symptom in another, and gates stop problems from stacking.

  1. Gate 0The firewall reaches the internet on its own public address.
  2. Gate 1The Google side is ready and nothing is billing yet.
  3. Gate 2The Google end of the tunnel exists and is waiting for the lab.
  4. Gate 3Phase 1 and phase 2 are up, and the tunnel interface is live.
  5. Gate 4BGP is established and routes are exchanged both ways.
  6. Gate 5Data flows end to end, and a full-size packet proves the MTU.
  7. Gate 6Firewall rules and route filters are tightened, and it all still works.
  8. Gate 7A deliberate break sends an alert email, and the incident closes on recovery.
  9. Gate 8VyOS does the same, in parallel, on interface 1.
  10. Gate 9Terraform describes what is running, and the plan says no changes.
Section 04

What broke, and what gave it away

The faults worth writing down are the ones where every individual piece looked right. Each of these ended with one command or one log line.

1

The firewall could not find its own gateway

The ISP handoff VLAN was allowed on the hypervisor's switch port but not on the link between two switches. Every setting I could see was correct. The break was in the middle.

show mac address-table vlan <ISP_VLAN> # only my own MAC, never the gateway
lesson check the path in the middle, not just the two ends
2

A pre-shared key that broke itself

The key was generated as base64. Its +, /, and = characters were mangled when pasted into a console, so the two ends no longer matched.

MAC mismatched # only the PSK differs at this point
fix openssl rand -hex 24, kept in Secret Manager
3

VyOS would not negotiate, and said little about why

Google reported a negotiation failure. The phase 1 proposal on VyOS was missing its Diffie-Hellman group, so the two sides never agreed on a proposal.

NEGOTIATION_FAILURE
fix dh-group 14 in phase 1, then count the lines
4

BGP said Established and advertised nothing

The session was up and healthy, but Google learned zero routes. The line that announces the lab network was the last line of the block, and it was the one that went missing in the paste.

numLearnedRoutes: 0
fix add the network statement, check received routes
5

The route filter ate every route

The inbound filter permitted 10.8.0.0/16 as an exact match. Google sends /24s, so nothing matched and everything was denied.

show ip bgp # empty right after adding the route maps
fix le 32 on FROM-GCP, soft reconfiguration to see what was dropped
6

An alert every night, while nothing was wrong

Tearing the tunnels down at the end of a session stops the metric, and the default setting treats missing data as a failure.

evaluation_missing_data = "EVALUATION_MISSING_DATA_INACTIVE"
fix missing data treated as empty, alert proven by a deliberate failure
Section 05

The cloud side as code

I built the Google side by hand first, with gcloud, so I understood every resource. Then I imported it into Terraform instead of rebuilding it, and nothing was applied until the plan showed zero to destroy.

Change the code to match reality. Never change reality to match the code.

The first import plan wanted to replace things I had not touched. Each one had a plain reason:

  • A peer gateway's description and redundancy type cannot be edited, only replaced, so both are copied exactly from what Google holds.
  • Google only returns a hash of the pre-shared key, so Terraform can never compare it. The key is ignored for drift, and a new version in Secret Manager replaces exactly that one tunnel.
  • The VM's service account was not declared, so Terraform planned to remove it. It is declared now.

After the apply, the BGP uptime kept counting instead of resetting, which proved nothing had been rebuilt, and the next plan said No changes.

Each router is one entry in a map. One variable builds or tears down the tunnels while the HA VPN gateway, and its two public addresses, stay in place:

# end of a session: no tunnels, no tunnel cost
terraform apply -var='enabled_tunnels=[]'

# start of a session: both tunnels back, about USD 0.10 an hour
terraform apply -var='enabled_tunnels=["opnsense","vyos"]'
Section 06

Security and cost

I treated every file as if it would be public, because it was always going to be.

  • Default-deny on both routers. IKE and ESP are accepted only from the Google peer address, and SSH listens on the lab LAN alone.
  • No public address on the cloud VM. I reach it through Identity-Aware Proxy, and Google's firewall admits only the two lab networks and IAP for SSH.
  • Keys never touch a file. Pre-shared keys live in Secret Manager and are read at the moment they are needed.
  • State is locked away. Terraform state holds secrets in plain text, so it sits in a versioned Cloud Storage bucket with public access prevention.
  • Keyless CI. A plan-only GitHub Actions workflow signs in through Workload Identity Federation, with actions pinned to commit SHAs, no permissions by default, and only the plan's summary line printed, because public repo logs are public.
  • Nothing real in the repo. Public addresses use documentation ranges, and gitleaks plus a private denylist hook block a commit that contains a real value.

Cost is part of security. Each tunnel costs about USD 0.05 an hour from the moment it exists, so the tunnels come down at the end of every session. The one dangerous step is a speed test left running: an hour at 1 Gbps is roughly 450 GB, about USD 54, so every test runs for a fixed 20 seconds.

Section 07

Lab versus production

This lab is not a high-availability design, and I would rather say so than have someone point it out. Two routers on two separate networks give two independent connections, not redundancy. If OPNsense fails, its network loses the cloud and VyOS cannot help.

In the labIn production
One tunnel per routerTwo tunnels per router, one to each HA VPN interface
Two routers, two networksOne network behind a shared gateway, both routers announcing it
Dead peer detection onlyBFD for sub-second failure detection
No BGP authenticationMD5 authentication on every session
Default route advertisementCustom advertisement with an explicit list
Default Compute service accountA dedicated account with only the roles it needs
Single regionGateways and Cloud Routers in more than one region
